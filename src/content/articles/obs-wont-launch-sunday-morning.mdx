## First: breathe. This is diagnosable in minutes.

It's 9:02, the service is at 10:00, and OBS — which worked *perfectly* last Sunday — bounces, hangs on its splash screen, or vanishes the instant it opens. Before anything else, hear the good news: launch failures are almost always an **initialization conflict** — a plugin, a graphics driver, or a corrupted config file failing during startup — and OBS ships with a tool built for exactly this morning. Work the list in order; most churches are streaming again by step two.

## The Sunday triage order

**1. Safe Mode — the two-minute save.** Modern OBS offers Safe Mode automatically after a crash, or **hold Shift while launching**. It starts OBS *without third-party plugins and scripts*. If it opens: you've both diagnosed the problem (a plugin) and rescued the service — your scenes and settings are intact, and whatever the missing plugin did is almost never essential to getting a Sunday stream out. Run the service in Safe Mode; hunt the culprit Tuesday.

**2. The plain reboot.** If you haven't restarted the *machine* (not just OBS), do it now. Half of "OBS won't launch" is a Windows update that half-applied overnight or a GPU driver in a bad state, and a clean boot clears it. (A pre-service restart should be [standard booth liturgy anyway](/kb/articles/livestream-stutters-40-minutes-in/).)

**3. Run as administrator, once.** Right-click → Run as administrator. If this works when normal launch doesn't, something changed permissions — usually security software. Note it for Tuesday.

**4. The config fallback.** If OBS still dies, a corrupted config from an unclean shutdown is likely. OBS keeps profiles and scene collections as files — if you [exported backups on a good week](/kb/articles/obs-settings-changed-between-sundays/) (you will after today), restoring is minutes. Without backups, a fresh OBS install with a single bare scene — one camera, one audio source — is an ugly but real way to be live by 10:00. The [OBS forums](https://obsproject.com/forum/) hold the deeper surgery for Monday.

**5. Call the help that can see.** If your church runs [Tech Manager](/tech-manager/), whoever's on call already has context — the machine's vitals, [what changed recently](/kb/articles/obs-help-from-home-sunday/), whether the box rebooted overnight — and [910-WORSHIP](/phone-support/) starts from your system's history rather than a description. A deliberate boundary worth knowing: a crashed OBS is **reported, never silently relaunched** by the automation, because [blind restarts can compound](/kb/articles/tech-manager-self-healing-explained/) exactly the corruption you're now managing.

## Why it broke when "nobody changed anything"

Because something did — it just didn't ask. Overnight Windows updates. GPU drivers that auto-refresh. A plugin that updated itself into a conflict (the single most common cause of launch instability — [more on the plugin question here](/kb/articles/obs-plugins-church-stream-safety/)). Or the machine was powered off mid-write last week and the config corrupted silently, waiting for the next launch to matter. Launch failures cluster on Sunday mornings for a simple reason: **Sunday is when the machine finally gets rebooted**, so six days of accumulated change all initializes at once, at the worst possible hour.

## The Tuesday disciplines that end the genre

1. **Updates happen midweek, then a full test.** Windows, GPU drivers, OBS, plugins — updated deliberately on Tuesday, followed by a complete launch-stream-record test (as a [draft run](/kb/articles/train-vmix-operators-without-risking-sunday/), so it pollutes nothing). Sunday machines never meet fresh software for the first time on Sunday. Disable what auto-updating you can; test after what you can't.
2. **Keep the service machine's plugin surface minimal.** Every plugin is an initialization risk. Experiments live in a test profile — or a test *machine* — not in Sunday's OBS.
3. **Export your baseline.** Profiles and scene collections, exported after every known-good change, stored somewhere findable. Ten minutes that turns step 4 above from a rebuild into a restore.
4. **Let monitoring notice the week for you.** [Pulse](/av-monitoring/) sees the reboot that happened Thursday at 3 a.m., the disk filling, [the drift that precedes failures](/kb/articles/obs-problem-every-sunday/) — so surprises get caught while they're still Tuesday problems.

And the meta-discipline underneath all four: a booth where [more than one person](/kb/articles/multiple-operators-obs-church/) can run the triage. The morning described at the top of this post is only a crisis when the one person who knows OBS is the one person who's unreachable — which is a [staffing pattern](/kb/articles/you-already-have-obs/), not a software one, and it's fixable for good.
